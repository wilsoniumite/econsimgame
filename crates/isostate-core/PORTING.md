# Porting notes: `isostate-core`

This crate is a Rust port of the Python package `isostate/` (the Isolated State
simulation: an agent-based spatial economy on a generated island, 1750 to 1900).
The Python package is the reference implementation and was not changed. The
port keeps the Python's structure, formulas and comments; it is meant to be the
long-term core of the game, with the Python kept as the oracle.

## Module mapping

The state is a plain struct of vectors (`State`), the content and parameters
are plain structs, and the simulation is free functions taking `&mut State`,
`&Content` and `&Params`, as in the Python.

| Python | Rust | Notes |
|---|---|---|
| `content.py` | `src/content.rs` | Same TOML (`data/content.toml`), parsed with serde; the default file is embedded at compile time |
| `params.py` | `src/params.rs` | `Params` struct with the Python defaults, overrides from TOML or JSON |
| `world.py` | `src/world.rs`, `src/ndimage.rs` | `ndimage.rs` holds the pieces of `scipy.ndimage` the world needs |
| `transport.py` | `src/transport.rs` | Cost graph, Dijkstra, catchments, traffic |
| `econ.py` | `src/econ.rs` | The monthly economy (`step_month`) |
| `land.py` | `src/land.rs` | Land allocation, urban growth, transport fields |
| `firms.py` | `src/firms.rs` | Productivity, site choice, entry, review, closures |
| `tech.py` | `src/tech.rs` | Discovery and diffusion |
| `people.py` | `src/people.rs` | Growth, migration, new towns |
| `rail.py` | `src/rail.rs` | Railway planning and construction |
| `names.py` | `src/names.rs` | Town, firm and person names |
| `observer.py` | `src/observer.rs` | Monthly series, yearly headlines |
| `record.py` | `src/record.rs` | `run.bin` snapshots and packing |
| `sim.py` | `src/sim.rs` | `init_state`, the yearly step, the run loop |
| `cli.py`, `__main__.py` | `src/cli.rs`, `src/main.rs` | `isostate-core run ...` |
| (dict keys of `st`) | `src/state.rs` | `State`, `Project`, `Event`, `Reason`, `MonthStats` |
| (numpy arrays) | `src/mat.rs`, `src/util.rs` | A row-major `Mat`; numpy's summation order, `bincount`, `argsort`, Python number formatting |
| (`numpy.random`) | `src/rng.rs` | Named streams, numpy's `choice` algorithms, replay of recorded draws |
| (none) | `src/families.rs`, `src/live.rs` | Additions for the game, off by default: families and the live API (FAMILIES.md) |
| (none) | `src/save.rs`, `src/sweep.rs`, `src/facts.rs` | Saved games, and the sweep of many seeds with its stylised facts (`docs/rules/README.md`); they change no run |
| (none) | `src/prices.rs`, `engel.rs`, `machines.rs`, `harvest.rs`, `chronicle.rs`, `works.rs`, `railways.rs` and `ways.rs`, `carting.rs`, `peopling.rs`, `towns.rs`, `mines.rs`, `canals.rs`, `landform.rs` with `landwater.rs` and `landcells.rs`, `accounts.rs` | The game's rules: a module for each mechanism, each off under `default_params()` and with a page under `docs/rules/` |

The public functions a binding (PyO3 later) needs are re-exported from the
crate root: `load_content` / `default_content`, `default_params` (and
`Params::from_toml_str`, `Params::from_json_str`, `Params::load`),
`init_state`, `step_month`, `step_year` (the yearly step, `sim::yearly`) and
`run(params) -> RunResult`. `sim::start`, `sim::run_month`, `sim::run_year`
and `sim::finish` split a run into pieces for a game loop.

## Building and testing

Always build with `-p isostate-core` (the workspace also holds the viewer).

```text
cargo build -p isostate-core --release
cargo test -p isostate-core --release
target/release/isostate-core run --seed 7 --regime landlords --out runs/rs_s7 [--end-year 1800] [--lite]
cargo run -p isostate-core --release --example timing        # a full run, timed by part
```

The CLI writes `run.bin`, `series_monthly.csv`, `events.json` and
`params.json` like `python3 -m isostate run`. It also takes `--params FILE`
(TOML or JSON overrides), `--content FILE` and `--quiet`, and, for what the
Python never had, `--rules game` and `--families N`; `isostate-core sweep`
runs many seeds at once (`docs/rules/README.md`). `isostate-core --help`
prints both.

The parity fixtures are generated by the Python package and are large (0.5 to
0.8 GB each), so they are not committed (`parity/fixtures/` is ignored). Without
them the parity tests print `SKIPPED` and pass; set `ISOSTATE_REQUIRE_PARITY=1`
to make them fail instead, and `ISOSTATE_PARITY_DIR` to read them from
elsewhere. To regenerate them, from the repository root:

```text
python3 crates/isostate-core/parity/dump_state.py --seed 7 --year 1752 --month 3 \
    --found-towns --stochastic --init --out crates/isostate-core/parity/fixtures/s7_1752
python3 crates/isostate-core/parity/dump_state.py --seed 7 --year 1786 --month 11 \
    --stochastic --whole-year --out crates/isostate-core/parity/fixtures/s7_1786
python3 crates/isostate-core/parity/dump_state.py --seed 7 --year 1843 --month 11 \
    --stochastic --whole-year --out crates/isostate-core/parity/fixtures/s7_1843
python3 crates/isostate-core/parity/dump_state.py --seed 7 --year 1847 --month 5 \
    --stochastic --whole-year --out crates/isostate-core/parity/fixtures/s7_1847
python3 crates/isostate-core/parity/record_run.py --seed 7 --end-year 1785 \
    --out crates/isostate-core/parity/fixtures/run_s7_1785
python3 crates/isostate-core/parity/dump_ndimage.py      # scipy.ndimage cases
```

Other scripts in `parity/`: `compare_runs.py` (the statistical table below),
`check_runbin.py` (compares the layout of a Rust and a Python `run.bin`),
`compare_worlds.py`, `world_stats.py`, `replay_world.py` and `replay_noise.py`
(world generator checks, with the `world_stats`, `world_dump` and `noise_dump`
examples).

The `world_dump` and `noise_dump` examples write their files, and
`replay_world.py` and `replay_noise.py` read them, in the directory named by
`ISOSTATE_WORLD_DIR`. With it unset they use `/tmp/worldcmp`, a Unix path: on
Windows that is `\tmp\worldcmp` on the current drive, so set the variable
there. The examples make the directory if it is missing.

```text
ISOSTATE_WORLD_DIR=out/worldcmp cargo run -p isostate-core --release --example world_dump -- 1
ISOSTATE_WORLD_DIR=out/worldcmp python3 crates/isostate-core/parity/replay_world.py
```

## How parity is tested

`dump_state.py` runs the Python simulation unchanged and, by wrapping module
functions, saves the whole state just before and just after one call of a step.
A Rust test loads the "before" state, runs the Rust step and compares every
field with the "after" state: relative tolerance 1e-9, with an absolute floor of
1e-12 times the largest magnitude in the array (for entries that are small
differences of large numbers, such as an inventory emptied to nearly zero).

Steps that draw random numbers are checked draw for draw. The dump runs them
with a recording copy of the numpy generator: a `Generator` subclass that logs
every number handed out, including the ones `Generator.choice` draws
internally. The Rust test replays those numbers (`rng::Rng::replaying`), so the
Rust step must make the same draws in the same order and reach the same
decisions; a leftover or missing draw, or a replayed integer out of range,
fails the test.

Two things in the Python are pinned for the fixtures:

- numpy's default `argsort` breaks exact ties in an order that depends on the
  CPU (the AVX-512, AVX2 and baseline builds give different orders; checked on
  this machine with `NPY_DISABLE_CPU_FEATURES`). The Python code sorts with
  ties in several places (the eight cheapest sites in `firms.candidate_cells`,
  the urban growth cells in `land.py`, the first roads, spur candidates), so a
  Python run is not reproducible from one machine to another. `dump_state.py`
  and `record_run.py` make every `np.argsort` without an explicit kind stable,
  ties by index, which is what the Rust port does.
- Nothing else: the state, the functions and the random streams are Python's.

### A whole run against Python

`record_run.py` records a whole Python run (every draw of every stream, the
world and every monthly series). The Rust test starts from Python's world,
replays the draws through the warm-up and 1750 to 1785, and compares the series.
Every draw lines up: all 205,369 draws of the firms stream, and those of the
names, tech and people streams, are consumed exactly, so every site picked, firm
founded and named and discovery made is the one Python made, for 46 simulated
years. The continuous values agree to rounding at first and then drift apart:

| Decade | Rust replay vs Python | Python vs Python, one-ulp change at the start |
|---|---|---|
| 1750s | 1.7e-10 | 4.2e-11 |
| 1760s | 5.4e-9 | 2.3e-11 |
| 1770s | 3.7e-4 | 9.1e-7 |
| 1780s | 4.5e-3 | 2.7e-5 |

(Largest relative difference over all 93 series; the most sensitive series is
the timber share of heating in both columns.) The right-hand column is the
Python model against itself after multiplying one town's population and one
price by 1 + 2^-52: the model amplifies rounding by roughly a factor of ten every
two to three years. The Rust run differs by rounding in every step rather than
once, and the wage search is a bisection (a rounding difference that flips the
sign of excess demand at a midpoint moves the wage by about 1e-12), so its drift
is larger, but it is the same amplification. In 1786 a near-tie falls the other
way in `firms.entry` and the draws stop lining up; the 1786 fixture shows that
the yearly step of 1786, started from Python's state, matches exactly. The test
checks that every draw lines up and that the 1750s agree to 1e-8.

### Outputs and the viewer

- `params.json` is byte for byte Python's. `series_monthly.csv` has the same
  header, the same CRLF line ends and Python's `%.6g` numbers. `events.json`
  has the same layout and escapes (Python's `ensure_ascii`, its rounding of
  floats to five decimals and `null` for non-finite numbers).
- `run.bin` has exactly Python's container layout (names, dtypes, shapes,
  alignment, header keys; checked with `parity/check_runbin.py` against a
  Python `run.bin`), including the display mixes and the lite variant.
- The Python HTML viewer loads Rust runs: `python3 -m isostate html` built a
  page from a Rust run plus a lite run, which loaded in headless Chromium
  without errors (151 years, 18 towns, 8,809 firms, 237 events, 92 series, the
  lite run recognised as the alternative).

## Timing

On this machine (2 vCPU Xeon at 2.1 GHz, idle), one full run (init, ten warm-up
years, 1750 to 1900, outputs) takes 21 s single-threaded in Rust and 107 to
120 s in Python (the README's 80 s was on another machine): about 5 times
faster. By part: the monthly economy 10.0 s (1,812 months), the yearly steps
10.0 s (of which the transport fields, one Dijkstra search per town and one
per good, are the largest part), start-up 0.9 s, observer and snapshots 0.3 s.

The target of a few seconds is not reached. Nothing is parallel yet, as asked.
The obvious next steps, in order of payoff:

1. Run the per-town Dijkstra searches and the per-good distance fields in
   parallel (they are independent; about half of the yearly time).
2. In `econ::step_month`, fuse the per-unit loops (land, labor and output of
   about 25,000 extractive units are each walked several times) and run the
   towns' wage searches in parallel.
3. Vectorise `exp`, `powf` and `ln` over the unit arrays.

## Deliberate deviations from the Python

- **Random numbers.** The streams (world, names, firms, tech, people, rail,
  misc) are PCG64 from `rand_pcg`, each seeded from the run seed and its index
  through SplitMix64. They are not numpy's streams, so a seed gives a different
  island in Rust than in Python. numpy's algorithms on top of the raw numbers
  are reproduced (`choice` with and without replacement and with weights,
  `uniform`, `integers`), which is what makes draw-for-draw replay possible.
- **Wage search.** Python bisects log wage 40 times per town and month,
  evaluating every unit's land demand at each step. Rust aggregates land demand
  per (town, sector), finds the root by a safeguarded Newton iteration on the
  aggregate, and then replays the 40 halvings, evaluating the full sum only at
  midpoints within 1e-11 of the root. The result is the same bisection result
  (checked: no differences over 92,736 town-months for each of seeds 7, 1 and
  3) at a fraction of the cost.
- **Rearranged powers.** Labor demand and output are written as
  `Lprev + k (x w^(-1/alpha) - Lprev)` and `A f lam (L/lam)^(1-alpha)` with the
  power of the wage computed once per town; same values to rounding.
- **Cached sector productivity.** `sector_tfp` depends only on (town, sector),
  so it is computed once per pair per month, not once per unit.
- **Dijkstra.** Path searches use a binary heap ordered as scipy's
  (`std::priority_queue` of (-distance, cell): shortest first, then the higher
  cell index), so predecessor trees match scipy's exactly, ties included.
  Distance-only fields (the per-good delivered price fields) use Dial's bucket
  queue, about twice as fast; distances do not depend on tie order. Railway
  route searches stop when the target is settled (its path is final then).
  Inactive towns are not searched (Python searches from a stand-in and then
  discards the result). The searches record their settle order, which
  `update_roads` walks backwards instead of sorting cells by distance again.
- **`update_transport`** does not end with `delta_fields`. In Python it does,
  and the yearly step (and `init_state`) calls `delta_fields` again after the
  land allocation, before anything reads the first result; Rust computes the
  fields once, at that second point.
- **Ties in `argsort` and `argmax`** are broken by index (stable order, first
  maximum), as numpy's `kind="stable"` and `argmax` do.
- **Summation order.** numpy's pairwise summation (blocks of 128, eight
  accumulators) is reproduced where Python sums contiguous arrays, as are
  `bincount`, `np.add.at` and axis sums in numpy's order; the matrix product in
  `tech.diffusion` is summed sequentially.
- **The cover passed to the graph.** Python passes the forest cover to
  `build_graph` by stashing it in the world dict (`world["_cover"]`); Rust
  passes it as an argument.
- **Parameters** are a typed struct: unknown keys are an error rather than
  ignored, and the regime is an enum (`landlords`, `commons`).
- **Content.** The default `data/content.toml` is embedded in the binary;
  `--content` reads another file.
- **JSON text** can differ from Python's in how a number is spelled (`1e-5`
  against `1e-05`), not in its value. `generated` dates are UTC.
- **The run loop** is split into `start`, `run_month`, `run_year` and
  `finish` for a game; the monthly money check returns an error instead of an
  assertion. Progress is printed every ten years.
- **HTML embedding** is not ported: `python3 -m isostate html` reads Rust
  `run.bin` files.
- `same_method_counts` skips methods without firms (their counts are zero);
  `use` is `land_use` and a project's `spur` is a bool.
- Extra modules with no Python counterpart: `state.rs`, `mat.rs`, `util.rs`,
  `rng.rs`, `ndimage.rs`.

## Known gaps

- Speed: 21 s, not a few seconds (see Timing).
- The cubic zoom in world generation matches scipy to 1e-12, not bit for bit.
- Whole runs match Python draw for draw only until a near-tie falls the other
  way (1786 for seed 7), as expected for a model that amplifies rounding.
- No PyO3 bindings yet; the public functions are shaped for them.
- The statistical comparison is over 16 seeds of one regime (landlords).
- The tests run the Python fixtures only if they have been generated (about
  3 GB in all).

## Things in the Python that look like bugs

Reported, not fixed: the Rust port does what the Python does in each case but
the first. How each fares under the game's rules was traced on 12 November
2026 (`docs/probes/tr-money.md`, sections 1 and 3), and is said at each item.

1. **Results depend on the CPU at ties.** `np.argsort` without `kind` breaks
   ties in a CPU-dependent order (AVX-512, AVX2 and baseline builds differ), and
   the code sorts tied values in `firms.candidate_cells` (the eight cheapest
   sites), `land.py` (urban growth cells), `sim.py` (first roads, `firm_at`)
   and `rail.plan_spurs` (candidates by flow). The same seed can give a
   different history on another machine. `kind="stable"` would fix it. The
   Rust does not share it, under either set of rules: `util::argsort` sorts
   (key, index) pairs, so ties fall to the lower index on every machine.
2. **Money grows more slowly than `money_growth`.** `econ.step_month` issues
   `money_growth / 12` times `money_total(st)`, but takes the total while the
   households' whole income for the month is in flight (their wages, their
   carting and both kinds of dividend, held in `hh_inc` until after the
   count), so it undercounts the stock: seed 7's money grows about 1.76 per
   cent a year rather than 2. What is left out is 11.5 to 14.7 per cent of the
   money, three quarters of it pay; dividends are a tenth to a seventh of it.
   It runs under both sets of rules (1.74 to 1.78 per cent a year under the
   game's), and under the game's the share left out also grows with what the
   merchants owe, since the count is of the money net. The pass over all the
   rules mends it for the game alone (`docs/designs/rules-pass.md`, 4.3).
3. **Spur proximity test.** `rail.plan_spurs` skips a mine near a finished spur
   with `abs(c - d) % W <= 3 and abs(c // W - d // W) <= 3`. The first part is
   not the column distance (`abs(c % W - d % W)` would be); it is true for cells
   whose flat indices differ by a multiple of `W` plus or minus up to 3. It
   does not run under the game's rules, which build no spurs:
   `rail::plan_spurs` returns at once when `railways.enabled` is on.
4. **Entry capital.** `firms.entry` doubles `K` when the return is above 0.6
   but keeps the rent bid and the inspector's record of the undoubled firm; and
   `limit = 1 + int(roi > 0.8)` can never matter, since there is at most one
   proposal per town and method. It does not run under the game's rules: with
   works sized to their market (`works::sized_entry`) the limit is one and
   there is no doubling.
5. **Footprint reservation.** `create_firm` adds the new firm's footprint to
   `cell_K_share`, but `after_transport` rebuilds `cell_K_share` from `f_K`
   (zero until built) at the end of the same year, so the reservation lasts
   only until then. Possibly intended. Under the game's rules it is mended:
   `works::land_held` counts capacity on order as well as built, so the
   rebuild keeps the ground of a works being built.
6. **Sister firm funding.** When `spawn_sister` cannot raise enough, the money
   taken from the parent firm goes to the town's households, not back to the
   parent. It runs under both sets of rules for a works no family owns (a
   family's goes back to the family). Counted on eight islands, a sister works
   failed to be funded once in 2,174 under the game's rules with six families,
   a family's, whose money went back to the family; and never in 25,286 under
   the port with none.
7. **Spur top-ups.** `rail.progress` tops up a project that ran short from the
   landlords of both its towns; a spur has the same town at both ends, so it
   draws twice from one town. It does not run under the game's rules: they
   build no spurs, and their own top-up (`ways.rs`) skips the second town when
   both ends are one.
8. **Resettlement.** `people.resettle_new_towns` moves population, cash and
   inventories from the donor town to the new one but copies a share of the
   donor's `outflow` without reducing the donor's (perhaps intended, as
   outflow is an expectation, not a stock). It does not run under the game's
   rules: households go with their cells (`peopling::move_with_cells`), which
   moves the outflow from the old town to the new.
9. **Unchecked donor.** `people.found_towns` takes `donor = catch[bc]`, which
   could be -1 for a cell outside every catchment; the site choice makes this
   unreachable at present. It does not run under the game's rules, which
   found towns by `peopling::found_towns`, only on cells that have a market.
10. **Dead state.** `f_out_acc`, `month_stats["share"]`, `bids`, `ag_labor`,
    `cell_firms`, `traffic`, `migration_flow`, `m_merch_margin`,
    `m_trade_value`, `cumprod_1750` and `subcost` are written but never read by
    the simulation; `firm_at` is read only to update itself. The port keeps
    them (some feed `run.bin` or the observer). Under the game's rules three
    are read: `migration_flow` by the chronicle, `bids` by the towns' rent
    floor, and `traffic` by the railways' and canals' books (`ways::note_year`),
    though nothing that decides reads the books.
